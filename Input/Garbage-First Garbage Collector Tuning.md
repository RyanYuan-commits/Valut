## 1	G1 的一般建议

G1 默认配置的目标是: 在高吞吐量的情况下提供相对较小切均匀的暂停.

- 如果注重高吞吐量, 可以使用 `-XX:MaxGCPauseMillis` 来放松暂停时间目标或提供更大的堆;
	
- 如果注重延迟, 则调低 `-XX:MaxGCPauseMillis` 参数.

避免通过 `-Xmn`, `-XX:NewRatio` 和其他选项来限制年轻代的大小, 因为年轻代大小是 G1 满足暂停时间目标的主要手段, 将年轻带大小设置为一个固定值会覆盖并实际上禁用暂停时间控制.

## 2	从其他收集器迁移到 G1

移除所有影响垃圾回收的选项，仅设置暂停时间, 堆大小, 可选择性的设置 `-Xms`;

许多对于其他收集器有用的选项对于 G1 可能完全不起作用, 如设置年轻代大小可能会完全组织 G1 调整年轻代大小来满足暂停时间的要求.

## 3	提高 G1 性能

应用级别的优化更有效, 如减少寿命较短的对象的数量;

通过设置 `-Xlog:gc*=debug` 观察日志, 日志在暂停期间和暂停之外提供了关于垃圾回收活动的详细概述.

### 3.1	避免频繁的 Full GC 

一次完整的 Full GC 非常耗时, 由于老年代堆占用过高引起的 Full GC 可以通过查找关键字 "Pause Full (Allocation Failure)" 来检测, 通常在这之前会出现遇到疏散失败的垃圾回收, 关键字为: `to-space exhausted`. 原因是应用程序分配了太多无法快速回收的对象, 并发标记未能及时完成以开始空间回收阶段, 分配许多大对象会增大遇到 Full GC 的概率, 由于这些对象在 G1 中的分配方式, 它们可能占用比预期更多的内存.
	
解决思路是确保并发标记及时完成, 可以通过减少老年代的分配率, 或者给并发标记更多的时间来完成.

- 通过 `gc+heap=info` 确定 Java 堆上巨大对象占用的区域数量, 关键字为 `Humongus regions: X->Y`, Y 给出由巨大对象占用的区域数量. 如果这个数量比老年代占用的区域数量较高, 可以通过 `-XX:G1HeapRegionSize` 来增大区域大小, 日志开头会打印当前区域的大小.
	
- 增大 Java 堆的大小, 这通常会增加标记所需的时间;
	
- 通过显示的设置 `-XX:ConcGCThreads` 来增大并发标记线程的数量;
	
- 将 G1 设置为更早开始标记, G1 会根据早期应用程序的行为自动确定 IHOP (Initiating Heap Occupancy Percent, 启动堆占用百分比) 阈值, 如果应用程序发生变化, 这个预测可能不正确, 有两种选择, 通过修改 `-XX:G1ReservePercent` 来增加自适应 IHOP 计算中使用的缓冲区, 或者使用 `-XX:-GUseAdaptiveIHOP` 和 `-XXInitiatingHeapOccupancyPercent` 手动设置 IHOP 来禁用它. 

### 3.2	拆解巨型对象

当分配空间给巨型对象的时候, 即使 Java 堆内存尚未耗尽, 也可能发生 Full GC, 因为 G1 需要找到连续的 Region 分配给大对象.

这种情况下可选的解决方法是增大堆内存或者增大 Region 的大小.

在极端情况下, 即使内存足够 G1 也可能找不到足够的连续空间来分配对象, 如果此次 Full GC 没有回收出足够大小的连续空间, 将导致虚拟机退出.

### 3.3	延迟优化

#### 3.3.1	高系统暂停时间

每次垃圾回收暂停 `[info] gc.cpu` 会输出一个类似这样的信息: `User=0.19s Sys=0.00s Real=0.01s`, 分别代表在虚拟机代码中花费的时间, 在操作系统中花费的时间和暂停期间经过的绝对时间, 如果系统时间相对较高大多数情况下是环境造成的, 已知的造成高系统时间的原因有:

- 虚拟机从重装系统内存中分配或释放内存可能会造成不必要的延迟, 可以通过 `-Xms` 和 `-Xmx` 将初始堆内存和最大堆内存设为相同的, 并使用 `-XX:+AlwaysPreTouch` 来预触碰所有内存, 将这些工作转移到虚拟机启动阶段, 从而在运行阶段避免这些延迟.
	
- 在 Linux 中, 通过 THP 功能将小页面合成大页面可能会随机暂停进程.
	
- 编写日志输出可能会暂停一段时间, 因为可能会存在某些后台任务会间歇的占用写入日志的硬盘所有的 IO 带宽, 建议为日志使用单独的磁盘或其他存储设备.

#### 3.3.2	引用对象处理耗时过长

引用处理阶段会显示处理 Reference Objects 所花费的时间信息. 在该阶段, G1 根据不同类型的引用对象(Reference Object)的要求更新其引用的对象(referent). 默认情况下, G1 尝试使用以下启发式规则并行化引用处理的子阶段:每 `-XX:ReferencesPerThread` 个引用对象启动一个线程, 但线程数受 `-XX:ParallelGCThreads` 参数值的限制. 此启发式规则可以通过以下方式调整:

- 设置 `-XX:ReferencesPerThread=0` 来禁用该规则, 默认使用所有可用线程;
	
- 设置 `-XX:-ParallelRefProcEnabled` 来完全禁用并行化.

#### 3.3.3	Young-Only Collections 中的 Young-Only 阶段耗时过长

正常的年轻代收集, 以及通常情况下的任何年轻代收集, 其耗时大致与年轻代的大小成正比, 或者更具体地说, 与收集集中需要复制的存活对象数量成正比. 如果 Evacuate Collection Set(疏散收集集) 阶段耗时过长, 特别是 Object Copy(对象复制) 子阶段, 请减小 `-XX:G1NewSizePercent`. 这会减小年轻代的最小尺寸, 从而可能缩短暂停时间.

如果应用程序性能, 特别是垃圾收集后存活对象的数量突然发生变化, 年轻代大小调整可能会出现另一个问题. 这可能导致垃圾收集暂停时间出现尖刺. 这种情况下, 使用 `-XX:G1MaxNewSizePercent` 来减小年轻代的最大尺寸可能会很有用. 这限制了年轻代的最大尺寸, 从而限制了暂停期间需要处理的对象数量.

#### 3.3.4	Mixed Collections 耗时过长

混合收集用于回收老年代的空间. 混合收集的收集集包含年轻代和老年代区域. 通过启用 `gc+ergo+cset=trace` 日志输出, 可以获取年轻代或老年代区域的疏散各占用了多少暂停时间的信息. 分别查看年轻代区域和老年代区域的预测年轻区域时间和预测老年代时间. 如果预测的年轻区域时间过长, 参照上一节处理. 否则, 为了减少老年代区域对暂停时间的贡献, G1 提供了三个选项:

- 通过增加 `-XX:G1MixedGCCountTarget`, 将老年代区域的回收分散到更多的垃圾收集中.
	
- 通过使用 `-XX:G1MixedGCLiveThresholdPercent`, 避免将那些回收耗时比例较大的区域放入候选收集集中, 从而避免收集它们. 在许多情况下, 存活对象占比高的区域收集起来非常耗时.
	
- 更早地停止老年代空间回收, 这样 G1 就不会收集那么多的存活对象占比高的区域. 在这种情况下, 增加 `-XX:G1HeapWastePercent`.

请注意, 最后两个选项会减少当前空间回收阶段可回收空间的候选收集集区域数量. 这可能意味着 G1 可能无法在老年代回收足够的空间以维持持续运行. 不过, 随后的空间回收阶段可能能够对它们进行垃圾收集.

#### 3.3.5	记忆集的更新和扫描时间过长

为了使 G1 能够疏散单个老年代区域, G1 会跟踪跨区域引用的位置, 即从一个区域指向另一个区域的引用. 指向给定区域的跨区域引用集合称为该区域的 **Remembered Set(记忆集)**. 当移动区域的内容时, 必须更新记忆集. 区域记忆集的维护大部分是并发进行的. 出于性能原因, 当应用程序在两个对象之间安装新的跨区域引用时, G1 不会立即更新该区域的记忆集. 记忆集更新请求会被延迟并批量处理以提高效率.

G1 进行垃圾收集需要完整的记忆集, 因此垃圾收集的 **Update RS** 阶段会处理任何未完成的记忆集更新请求. **Scan RS** 阶段在记忆集中搜索对象引用, 移动区域内容, 然后将这些对象引用更新到新位置. 根据应用程序的不同, 这两个阶段可能花费大量时间.

- 使用选项 `-XX:G1HeapRegionSize` 调整堆区域的大小会影响跨区域引用的数量以及记忆集的大小. 处理区域的记忆集可能是垃圾收集工作的很大一部分, 因此这对可达到的最大暂停时间有直接影响. 较大的区域往往具有较少的跨区域引用, 因此处理它们的相对工作量会减少, 尽管同时较大的区域可能意味着每个区域需要疏散更多存活对象, 从而增加其他阶段的时间.

- G1 尝试调度记忆集更新的并发处理, 以便 Update RS 阶段占用大约 `-XX:G1RSetUpdatingPauseTimePercent` 百分比的允许最大暂停时间. 通过减小该值, G1 通常会在并发阶段执行更多的记忆集更新工作.
	
- 如果看到 Update RS 时间突然升高, 且应用程序同时分配大对象, 这可能是由一种试图通过批量处理来减少并发记忆集更新工作的优化引起的. 如果创建此类批次的应用程序行为恰好发生在垃圾收集之前, 那么垃圾收集必须在暂停的 Update RS 阶段处理所有这些工作. 使用 `-XX:-ReduceInitialCardMarks` 可禁用此行为并潜在地避免这些情况.
	
- Scan RS 时间还取决于 G1 为保持记忆集存储大小较低而执行的压缩量. 记忆集在内存中存储得越紧凑, 在垃圾收集期间检索存储值所需的时间就越长. G1 会根据该区域记忆集的当前大小, 在更新记忆集时自动执行这种称为 **记忆集粗化** 的压缩. 特别是在最高压缩级别, 检索实际数据可能非常慢. 选项 `-XX:G1SummarizeRSetStatsPeriod` 结合 `gc+remset=trace` 级别的日志会显示是否发生了这种粗化. 如果发生, 则“Before GC Summary”部分中的 `Did <X> coarsenings` 行中的 `<X>` 会显示一个较高的值. 可以显著增加 `-XX:G1RSetRegionEntries` 选项以减少这种粗化的数量. 避免在生产环境中使用这种详细的记忆集日志记录, 因为收集这些数据可能需要大量时间.

#### 3.3.6	针对吞吐量的调优

G1 的默认策略试图在吞吐量和延迟之间保持平衡; 然而, 在某些情况下, 我们更希望获得更高的吞吐量. 除了像前几节描述的那样减少总体暂停时间外, 还可以降低暂停的频率. 主要思路是通过使用 `-XX:MaxGCPauseTime` 增加最大暂停时间目标. 分代大小启发式算法将自动调整年轻代的大小, 这直接决定了暂停的频率. 如果这没有产生预期的行为, 特别是在空间回收阶段, 使用 `-XX:G1NewSizePercent` 增加年轻代的最小大小将强制 G1 这样做.

在某些情况下, `-XX:G1MaxNewSizePercent` (允许的最大年轻代大小) 可能会通过限制年轻代大小来限制吞吐量. 这可以通过查看 `gc+heap=info` 日志输出的区域摘要来诊断. 在这种情况下, Eden 区和 Survivor 区的总百分比接近 `-XX:G1MaxNewSizePercent` 占总区域数的百分比. 在这种情况下, 应考虑增加 `-XX:G1MaxNewSizePercent`.

提高吞吐量的另一个选择是尝试减少并发工作量, 特别是并发记忆集更新通常需要大量的 CPU 资源. 增加 `-XX:G1RSetUpdatingPauseTimePercent` 会将工作从并发操作转移到垃圾收集暂停中. 在最坏的情况下, 可以通过设置 `-XX:-G1UseAdaptiveConcRefinement -XX:G1ConcRefinementGreenZone=2G -XX:G1ConcRefinementThreads=0` 来禁用并发记忆集更新. 这主要禁用了该机制, 并将所有记忆集更新工作转移到下一次垃圾收集暂停中.

使用 `-XX:+UseLargePages` 启用大页内存的使用也可以提高吞吐量. 有关如何设置大页内存, 请参阅您的操作系统文档.

您可以通过禁用堆调整功能来最大限度地减少堆调整工作;将选项 `-Xms` 和 `-Xmx` 设置为相同的值. 此外, 您可以使用 `-XX:+AlwaysPreTouch` 将操作系统的虚拟内存映射到物理内存的工作转移到 VM 启动时间. 这两项措施对于使暂停时间更加一致特别有效.

#### 3.3.7	针对堆大小的调优

与其他收集器一样, G1 旨在调整堆的大小, 以便垃圾收集所花费的时间低于由 `-XX:GCTimeRatio` 选项确定的比率. 调整此选项以使 G1 满足您的要求.
