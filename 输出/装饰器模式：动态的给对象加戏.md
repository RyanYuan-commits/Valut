## 1	使用场景

### 1.1	出现 “组合爆炸” 趋势

> 有一个 `BasicDataProcessor`，为了加密功能，写一个 `EncryptedDataProcessor`，为了压缩功能写一个 `CompressedDataProcessor`；而如果要求既加密又压缩，要再写一个 `EncryptedAndCompressedDataProcessor` 吗？

==判断标准==：当功能可以任意叠加时，且每种叠加都用继承来实现会导致**类数量激增**。

此时可以添加一个 `DataProessorDecorator` 接口，继承 `BasicDataProcessor` 接口，添加子类 `EncrptedDataProcessorDecorator` 和 `CompressedDataProcessorDecorator` 分别实现加密和压缩功能；后续如果要实现加密 + 压缩，使用这两个子类的组合来实现；后续要添加其他功能，只需要添加新的装饰器即可，避免类数量激增的问题。

### 1.2	在无法修改代码的情况下实现拓展

> 需要拓展的类被 `final` 修饰，或者代码与大量模块耦合，牵一发而动全身，如何在不修改代码的情况下实现拓展呢？

==判断标准==：必须在运行时，为某个特定的实例新增功能，且不能干扰其他实例。

添加一个装饰器，将拓展内容写在装饰器中，运行时将实例装配到装饰器中，执行装饰器对应方法即可。

### 1.3	逻辑具有 “剥洋葱” 的特性

> 需要编写的业务逻辑是一层套一层的，比如 权限检查 -> 缓存校验 -> 日志记录 -> 核心代码

==判断标准==：这些逻辑是正交的（互不影响），且希望可以自由的拆卸和调整它们的顺序；场景一的拓展也需要满足这个标准。

## 2	代码案例

初始只有要给基础的发送功能；

```java
public interface MsgSender {
    void send(String msg);
}

public class BasicSender implements MsgSender {
    @Override
    public void send(String msg) {
        System.out.println("发送基础消息: " + msg);
    }
}
```

构建装饰器，在此基础上实现加密和日志功能：

```java
// 1. 装饰器基类：必须实现相同的接口，并持有一个接口引用
public abstract class SenderDecorator implements MsgSender {
    protected MsgSender wrapped; // 被装饰的对象

    public SenderDecorator(MsgSender sender) {
        this.wrapped = sender;
    }

    @Override
    public void send(String msg) {
        wrapped.send(msg); // 默认行为是委派给原对象
    }
}

// 2. 具体的装饰实现：加密
public class EncryptDecorator extends SenderDecorator {
    public EncryptDecorator(MsgSender sender) { super(sender); }

    @Override
    public void send(String msg) {
        String encrypted = "【加密】" + msg; // 增加的功能
        super.send(encrypted);
    }
}

// 3. 具体的装饰实现：日志
public class LogDecorator extends SenderDecorator {
    public LogDecorator(MsgSender sender) { super(sender); }

    @Override
    public void send(String msg) {
        super.send(msg);
        System.out.println("日志：消息发送完毕。"); // 增加的功能
    }
}
```

此时就可以随意组合使用这些功能。

```java
public class Main {
    public static void main(String[] args) {
        // 想要一个既能加密又能打日志的发送器
        MsgSender sender = new LogDecorator(new EncryptDecorator(new BasicSender()));
        
        sender.send("Hello World");
    }
}
```

## 3	总结

装饰器模式的本质是：持有同类实例的引用 + 覆写方法；

和代理模式很像，但是它们的侧重点不同：代理模式更偏向于控制，装饰器模式更偏向于增强。
