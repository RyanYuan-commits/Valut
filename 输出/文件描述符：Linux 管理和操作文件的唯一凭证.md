在 Linux 中一切皆文件，不管是硬盘上的数据，还是键盘、显示器等硬件设备，还是网络通信中的 Socket 连接，在 Linux 的眼中，都是“文件”；文件描述符（File Descriptor）是操作系统用来**管理和操作**这些文件的**唯一凭证**。

---

## 1	非负整数

在用户态的应用程序代码中，文件描述符表现为一个非负整数。

当启动任何一个 Linux 进程时，操作系统默认会为这个进程自动打开三个标准文件：

- `0` (Standard Input / STDIN)：标准输入，通常是键盘；
- `1` (Standard Output / STDOUT)： 标准输出，通常是显示器/终端；
- `2` (Standard Error / STDERR)： 标准错误输出，也是显示器，用于区分正常输出和报错。

## 2	FD 的维护方式

### 2.1	进程级 FD 表

每个进程的进程控制块（PCB）中都有一张自己专属的表，这个表的数据类型是数组，数组的下标就是 FD 的非负整数表示。

数组的元素不是文件本身，而是指向内核中的系统级打开文件表的指针。

### 2.2	系统级打开文件表

系统级打开文件表所有进程共享，当一个文件被打开时，内核会在这个表中创建一个条目，条目中记录了这个文件的动态信息：

- 文件偏移量 (File Offset)： 记录当前文件读/写到哪个位置了；
- 访问模式 (Access Mode)： 你是只读打开、只写打开，还是读写打开（O_RDONLY, O_WRONLY 等）；
- 状态标志： 比如是否是非阻塞模式（O_NONBLOCK）；
- 引用计数 (Reference Count)： 记录有多少个 FD 指向这个条目。只有当引用计数降为 0 时，内核才会真正释放这块资源；
- 一个指向 i-node 表的指针。

### 2.3	文件系统 i-node 表

位于文件系统中，用于存储文件的静态物理信息的表，无论一个文件被打开多少次，在 i-node 中只会有唯一一个条目，这个条目中存储了文件的物理位置、文件大小、文件的所有者和权限。

---

当使用 `read(fd, buffer, 1024)` 读取一个文件时，进程会先查找自己的 FD 表，然后通过内部的指针找到系统打开文件表获取当前的读写位置，再通过指针找到 i-node 表定位数据位置，最后将数据读入内存。

---

## 3	FD 相关的系统限制

由于维护 FD 的三张表需要消耗**内核内存**，操作系统对 FD 设置了配额，这个限制分为三个级别：

- ==系统级的限制==：整个 Linux 系统中的所有进程能打开多少 FD，这个数量通常非常大，比如几百万，很少会触顶；
- ==进程级的限制==：限制单个进程能打开 FD 的数量，绝大多数的 “Too many open files” 都是因为触发了这个限制。

Linux 默认的进程级限制是 1024，这意味着即使服务器的内存再大，最多也只能同时维持 1024 个网络长连接，可以通过编辑 `/etc/security/limits.conf` 来修改：

```
* soft nofile 1000000
* hard nofile 1000000
```

除了并发真的高之外，报错的另一个常见原因是代码问题，如果不断地创建新连接或打开新文件，但是在业务逻辑结束后忘记调用 `close(fd)` 或者 `channel.close()`，那个进程的 FD 表里的条目就会一直被霸占。随着时间推移，FD 被耗尽，系统就会拒绝一切新的连接和文件读写。
