场景：海量定时任务的管理问题

**单定时器方案**：将所有的定时任务放到 set 中，启动一个定时器，定时轮询这个 set，执行定时结束的任务；在小批量场景下可行，如果任务过多，会出现任务无法按照定时时间执行的问题。

**多定时器方案**：为每个任务启动一个定时器，但是资源开销过大，一般不会采用。

**Redis 的过期通知功能**：基于 Redis 的发布/订阅机制，但是需要面对 Redis 发布订阅的不稳定或可靠性问题。

**Hash 分层时间轮算法**：为大批量定时任务管理而生。

---

时间轮是一个被切分为多个部分的环形数组，定时任务被放置在时间轮中，调度器以固定的速率扫描这个环形数组，在扫描过程中遇到定时结束的任务，执行。

被划分的每个部分成为一个 Bucket，扫过一个 Bucket 的时间称为时间槽间隔（si），如果有 N 个 Bucket，遍历一遍时间轮就需要 N 乘以 si 的时间。

要提高执行精度，需要降低 si；要提高执行效率，则要求每个 Bucket 中的任务尽量少，也就是提高 N。

---

时间轮是一个高性能，低消耗的数据结构，适用于非准实时，且执行速度快的场景，如心跳检测。

---

一个时间轮至少需要提供四种功能：加入任务、执行任务、删除任务、按照时间刻度运行

---

**时间刻度不够用的问题**：如果时间不止局限在一天内，会遇到时间刻度不够用的问题，此时可以选择增加时间刻度、为时间轮添加 round 属性以及选用分层时间轮的实现方案；

**增加时间刻度**的方案可能会导致时间轮利用率过低的问题；

**为时间轮增加 round 属性**：在存入任务的时，在计算出任务在第几个 Bucket 的同时计算出任务需要时间轮走多少圈可以到达，每当指针抵达一个 Bucket 时，将所有任务的 Round 减一，选出 Round 为 0 的任务执行。

> [!note] 在任务中记录 round 和记录 deadline 的方案对比
> 在任务中记录 round 
> - 优势：计算逻辑简单，不依赖系统 API 获取系统时间，也就不会受到系统时间的影响
> - 缺陷：短暂抖动的影响会被放大到整个执行过程，如系统发生 Full GC 暂停 3s，之后执行的所有任务都会被推迟三秒；
> 
> 在任务中记录 deadline
> - 优势：计算精度更高、不易受到系统抖动的影响
> - 缺陷：依赖系统 API 获取系统时间、可能带来并发的瞬时风暴（如果系统出现抖动，可能有大量到期的任务并发执行）
> 
> 两者也存在共同的缺陷：对于每个 bucket 均需要遍历来执行比较或计算（时间复杂度问题）

**选用分层时间轮的实现方案**：
在时间复杂度上，保障每次扫描到的任务都是需要执行的，无需复杂的遍历；
在空间复杂度上，采用了分层的策略。

我们的任务可能涉及四个时间单位：小时、天、周、月，可以构建四个维度的时间轮，当一个任务在某个时间轮上被扫描到，那么它一定会被移动到新的更低维度的时间轮或执行，这样就避免了频繁遍历的问题；

==io.netty.util.HashedWheelTimer 代码分析学习==

HashedWheelTimer 构造方法：

- 时间轮的大小是 2 的幂次，便于后续计算，将十进制运算转化为对应的二进制运算是常用的优化策略；
- tickDuration：是每个时间轮的跨度，使用纳秒表示；
- Netty 将工作线程封装为 WorkerThread。

```java
public HashedWheelTimer(  
        ThreadFactory threadFactory,  
        long tickDuration, TimeUnit unit, int ticksPerWheel, boolean leakDetection,  
        long maxPendingTimeouts, Executor taskExecutor) {  
  
    // 对传入参数的检查... 
  
    //【关键方法】将 ticksPerWheel 转化为 2 的幂次并初始化时间轮
    wheel = createWheel(ticksPerWheel);  
    mask = wheel.length - 1;  
  
    // Convert tickDuration to nanos.  
    long duration = unit.toNanos(tickDuration);  
  
    // Prevent overflow.  
    if (duration >= Long.MAX_VALUE / wheel.length) {  
        throw new IllegalArgumentException(String.format(  
                "tickDuration: %d (expected: 0 < tickDuration in nanos < %d",  
                tickDuration, Long.MAX_VALUE / wheel.length));  
    }  
  
    if (duration < MILLISECOND_NANOS) {  
        logger.warn("Configured tickDuration {} smaller than {}, using 1ms.",  
                    tickDuration, MILLISECOND_NANOS);  
        this.tickDuration = MILLISECOND_NANOS;  
    } else {  
        this.tickDuration = duration;  
    }  
  
    workerThread = threadFactory.newThread(worker);  
  
    leak = leakDetection || !workerThread.isDaemon() ? leakDetector.track(this) : null;  
  
    this.maxPendingTimeouts = maxPendingTimeouts;  
  
    if (INSTANCE_COUNTER.incrementAndGet() > INSTANCE_COUNT_LIMIT &&  
        WARNED_TOO_MANY_INSTANCES.compareAndSet(false, true)) {  
        reportTooManyInstances();  
    }  
}
```
